# 02. Arquitectura General

## 1. Introducción

Este documento define la arquitectura general del frontend de TechSupply SCM, estableciendo la organización de sus principales capas, la forma en que interactúan entre sí y los principios que regirán el desarrollo de la aplicación.

Su objetivo es proporcionar una visión global del funcionamiento del frontend antes de abordar aspectos específicos como la estructura del proyecto, el sistema de navegación, los componentes reutilizables o el consumo de servicios.

La arquitectura propuesta busca mantener una clara separación de responsabilidades, facilitar el mantenimiento del código y permitir la incorporación de nuevos módulos sin afectar la estructura existente.

---

## 2. Objetivos de la Arquitectura

La arquitectura del frontend ha sido diseñada con los siguientes objetivos:

- Separar claramente la presentación de la lógica de comunicación.
- Favorecer la reutilización de componentes.
- Centralizar el consumo de la API REST.
- Facilitar el mantenimiento del código.
- Permitir el crecimiento del sistema mediante módulos independientes.
- Mantener una experiencia de usuario consistente en toda la aplicación.
- Preparar la aplicación para futuras ampliaciones del sistema TechSupply SCM.

---

## 3. Arquitectura en Capas

El frontend estará organizado en varias capas funcionales, donde cada una tendrá responsabilidades claramente definidas.

```text
                    Usuario
                        │
                        ▼
                 Interfaz React
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
     Layouts         Pages        Shared UI
        │               │               │
        └───────────────┼───────────────┘
                        ▼
                   Services
                        │
                        ▼
                  Axios Client
                        │
                        ▼
                 API REST (Node.js)
                        │
                        ▼
                      MySQL
```

Cada capa interactúa únicamente con la inmediatamente inferior, evitando dependencias innecesarias y manteniendo una arquitectura desacoplada.

---

### 3.1 Usuario

Representa al operador que interactúa con el sistema mediante la interfaz web.

Todas las acciones realizadas por el usuario generan solicitudes hacia la aplicación React.

---

### 3.2 Interfaz React

Constituye el núcleo del frontend.

Es responsable de:

- Renderizar la interfaz.
- Gestionar la navegación.
- Mostrar la información obtenida del backend.
- Capturar las acciones del usuario.

No contiene reglas de negocio.

---

### 3.3 Layouts

Los Layouts definen la estructura visual compartida entre múltiples páginas.

Ejemplos:

- Barra de navegación.
- Menú lateral.
- Encabezado.
- Área principal de contenido.
- Pie de página (si aplica).

Su propósito es proporcionar una experiencia uniforme durante toda la navegación.

---

### 3.4 Pages

Las páginas representan cada uno de los módulos funcionales del sistema.

Cada página coordina la interacción entre los componentes visuales y los servicios que consumen la API.

Las páginas no implementan lógica de negocio.

Su responsabilidad consiste en organizar la información correspondiente a un proceso específico.

---

### 3.5 Shared UI

Corresponde al conjunto de componentes reutilizables de la aplicación.

Ejemplos:

- Botones.
- Tablas.
- Formularios.
- Modales.
- Alertas.
- Indicadores de carga.
- Badges de estado.
- Tarjetas informativas.

Estos componentes serán utilizados por todos los módulos del sistema.

---

### 3.6 Services

Los servicios constituyen la capa de comunicación con el backend.

Cada servicio encapsula las llamadas HTTP correspondientes a un módulo específico.

Ejemplos:

- cliente.service.js
- pedido.service.js
- despacho.service.js
- ruta.service.js

Los componentes visuales nunca realizarán solicitudes HTTP directamente.

Toda comunicación con la API deberá realizarse a través de esta capa.

---

### 3.7 Axios Client

Representa un único punto de acceso para todas las solicitudes HTTP.

Será responsable de:

- Configurar la URL base del backend.
- Enviar peticiones HTTP.
- Centralizar configuraciones comunes.
- Facilitar futuras incorporaciones como autenticación mediante tokens o interceptores.

---

### 3.8 Backend

El backend concentra toda la lógica del negocio.

El frontend únicamente consume los servicios expuestos mediante la API REST.

---

## 5. Principios Arquitectónicos

### 5.1 Desacoplamiento

El frontend estará completamente desacoplado del backend.

La única dependencia entre ambos será el contrato definido por la API REST.

Esto implica que:

- El frontend no conoce la base de datos.
- El frontend no conoce Sequelize.
- El frontend no conoce Python.
- El frontend no conoce n8n.
- El frontend no conoce la implementación interna del backend.

Únicamente conoce los endpoints expuestos por la API.

---

### 5.2 Modularidad

Cada módulo del sistema estará aislado del resto.

Por ejemplo:

```text
Clientes
│
├── Pages
├── Components
├── Services

Pedidos
│
├── Pages
├── Components
├── Services

Despachos
│
├── Pages
├── Components
├── Services
```

Esta organización permitirá desarrollar, mantener y ampliar cada módulo de manera independiente.

---

### 5.3 Comunicación entre Módulos

Los módulos no deberán comunicarse directamente entre sí.

Toda interacción se realizará mediante:

- Navegación entre páginas.
- Estado compartido cuando sea necesario.
- Consumo de la API.

De esta manera se evita el acoplamiento entre funcionalidades.

---

### 5.4 Escalabilidad

La arquitectura ha sido diseñada para soportar la futura incorporación del módulo Inbound.

La integración de nuevos módulos no requerirá modificar la estructura existente, sino únicamente agregar nuevas funcionalidades siguiendo los mismos principios arquitectónicos.

Esto permitirá evolucionar el sistema hacia una solución integral de gestión de suministros.

---

## 6. Beneficios de la Arquitectura

La arquitectura propuesta ofrece las siguientes ventajas:

- Alta mantenibilidad.
- Escalabilidad modular.
- Componentes reutilizables.
- Separación clara de responsabilidades.
- Facilidad para realizar pruebas.
- Bajo acoplamiento entre módulos.
- Integración sencilla con nuevas funcionalidades.
- Consistencia en el desarrollo de toda la aplicación.

## 8. Decisiones Arquitectónicas

Durante el diseño del frontend se adoptaron las siguientes decisiones:

- React será el framework principal de la aplicación.
- Se utilizará JavaScript (ES6+) en lugar de TypeScript para mantener la simplicidad del MVP.
- Axios centralizará toda la comunicación con la API REST.
- Bootstrap será el sistema base de estilos.
- React Router gestionará toda la navegación.
- Redux no será incorporado en esta primera versión.
- Toda la lógica de negocio permanecerá exclusivamente en el backend.
