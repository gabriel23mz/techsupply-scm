# 04A. Arquitectura Funcional del Frontend

## 1. Introducción

### Objetivo

Definir la arquitectura funcional del frontend de TechSupply SCM, describiendo el comportamiento esperado de cada módulo desde la perspectiva del operador del sistema.

Este documento constituye la referencia funcional principal del frontend para el módulo Outbound y establece cómo el usuario interactúa con la aplicación durante la ejecución de los procesos de negocio.

Su propósito es documentar el funcionamiento de la interfaz, los flujos de trabajo y la interacción entre el operador y el sistema, sin abordar detalles de implementación técnica ni decisiones específicas del desarrollo.

### Alcance

La arquitectura funcional comprende exclusivamente los módulos considerados dentro del alcance del proyecto académico correspondiente al módulo Outbound.

Los módulos documentados son:

- Dashboard
- Gestión de Clientes
- Gestión de Ubicaciones
- Gestión de Pedidos
- Workspace de Detalles de Pedido
- Gestión de Rutas
- Centro de Operaciones Logísticas

Cada uno representa una etapa específica del proceso operativo y contribuye al flujo general de logística de salida.

### Organización del documento

El documento se organiza siguiendo el recorrido funcional que realiza el operador dentro del sistema.

En primer lugar se presentan los principios que orientan el diseño del frontend y el flujo operativo general. Posteriormente se describe el comportamiento funcional de cada módulo, indicando su propósito, responsabilidades, información presentada al usuario, acciones disponibles y relación con el resto del proceso de negocio.

Esta organización permite comprender el funcionamiento integral de la aplicación antes de abordar los aspectos técnicos descritos en los documentos de arquitectura posteriores.

---

## 2. Filosofía de Diseño Operativo

La arquitectura funcional del frontend se fundamenta en una filosofía orientada a procesos, donde cada módulo representa una etapa del flujo operativo y la interfaz acompaña al operador durante toda la ejecución de sus actividades.

El sistema no se concibe como un conjunto de pantallas independientes, sino como un entorno de trabajo continuo que facilita la transición entre las distintas etapas del proceso logístico.

Para lograrlo, el diseño del frontend se apoya en los siguientes principios.

### Interfaz orientada al proceso

La navegación sigue el mismo orden lógico con el que se desarrollan las operaciones del negocio. Cada módulo prepara la información necesaria para el siguiente, favoreciendo la continuidad del trabajo y reduciendo desplazamientos innecesarios entre pantallas.

Cuando una tarea finaliza, la interfaz propone naturalmente el siguiente paso del proceso, manteniendo el contexto operativo del usuario.

### Workspace como unidad principal de trabajo

Las operaciones simples se realizan mediante pantallas tradicionales de consulta y mantenimiento.

Sin embargo, cuando una actividad requiere trabajar durante varios minutos sobre una misma entidad, el sistema utiliza un Workspace especializado que concentra toda la información necesaria para completar el proceso sin abandonar la pantalla.

Este enfoque permite consultar información relacionada, registrar datos, realizar modificaciones y supervisar el estado general de la operación desde un único espacio de trabajo.

### Persistencia inmediata

Cada acción confirmada por el operador se almacena inmediatamente en el backend mediante una solicitud independiente.

No existen formularios con múltiples cambios pendientes de guardar, lo que reduce el riesgo de pérdida de información y mantiene sincronizados el frontend y la API durante toda la operación.

### Separación de responsabilidades

Toda la lógica de negocio permanece centralizada en el backend.

El frontend se limita a presentar información, capturar las acciones del usuario, consumir los servicios expuestos por la API y proporcionar retroalimentación visual sobre el resultado de cada operación.

Esta separación favorece el mantenimiento del sistema y permite evolucionar la lógica del negocio sin afectar la experiencia del usuario.

### Consistencia de la experiencia de usuario

Todos los módulos mantienen una estructura visual y funcional homogénea.

Los formularios, tablas, acciones principales, filtros y mecanismos de navegación conservan un comportamiento consistente a lo largo de toda la aplicación, reduciendo la curva de aprendizaje y facilitando el trabajo diario del operador.

## 3. Flujo General del Operador

El frontend ha sido diseñado para reflejar el flujo operativo implementado por el módulo Outbound.

Cada módulo representa una etapa específica del proceso y prepara la información necesaria para la siguiente, permitiendo que el operador complete sus actividades de forma continua.

El recorrido funcional principal es el siguiente.

```text
Dashboard
      │
      ▼
Gestión de Clientes
      │
      ▼
Gestión de Pedidos
      │
      ▼
Workspace de Detalles de Pedido
      │
      ▼
Pedido Listo para Despacho
      │
      ▼
Centro de Operaciones Logísticas
      │
      ▼
Despacho en Tránsito
      │
      ▼
Entrega del Pedido
```

Aunque cada módulo puede consultarse de manera independiente, la interfaz favorece la continuidad del proceso mediante transiciones naturales entre las diferentes etapas.

Durante este recorrido, el operador registra clientes cuando es necesario, crea pedidos, incorpora los productos mediante el Workspace, prepara el despacho y realiza el seguimiento de la distribución hasta la entrega final.

Este flujo constituye la base sobre la cual se diseñan los módulos funcionales descritos en las secciones siguientes.

## 4. Módulos Funcionales

### 4.1 Dashboard

#### Objetivo

Proporcionar al operador una visión general del estado actual de la operación logística al iniciar la aplicación, mediante indicadores relevantes y accesos rápidos a los principales módulos del sistema.

El Dashboard constituye la pantalla inicial de TechSupply SCM y funciona como punto de partida para las actividades diarias del operador. Su finalidad no es administrar información, sino facilitar la supervisión de la operación y agilizar el acceso a las funcionalidades más utilizadas.

---

#### Responsabilidad del módulo

El Dashboard es responsable de presentar información resumida sobre el estado general del sistema y facilitar el inicio del flujo operativo.

Sus principales responsabilidades son:

- mostrar indicadores operativos;
- resumir el estado de los pedidos;
- resumir el estado de los despachos;
- ofrecer accesos rápidos a los módulos principales.

No realiza operaciones de creación, modificación o eliminación de información, ya que estas permanecen delegadas a los módulos especializados.

---

#### Importancia dentro del sistema

El Dashboard representa el punto de entrada del operador a la aplicación.

Antes de iniciar cualquier proceso, permite conocer rápidamente el estado de la operación y decidir la siguiente actividad a realizar.

Entre la información que puede visualizarse se encuentra:

- pedidos pendientes de preparación;
- pedidos listos para despacho;
- despachos en curso;
- entregas realizadas durante la jornada.

Esta visión inicial proporciona el contexto necesario para iniciar el trabajo diario.

---

#### Relación con el flujo operativo

A diferencia de los demás módulos, el Dashboard no constituye una etapa del proceso de negocio, sino el punto de acceso hacia los distintos procesos operativos.

Su participación dentro de la aplicación puede representarse de la siguiente manera:

```text
Inicio de sesión

↓

Dashboard

↓

Seleccionar módulo

↓

Continuar proceso operativo
```

Desde esta pantalla el operador podrá acceder al módulo requerido según las necesidades de la operación.

---

#### Información presentada

La información mostrada corresponde a indicadores consolidados obtenidos desde el backend.

Entre los principales indicadores se incluyen:

- pedidos registrados;
- pedidos listos para despacho;
- despachos activos;
- despachos entregados;
- clientes registrados;
- ubicaciones registradas;
- rutas configuradas.

Estos indicadores permiten conocer rápidamente el estado del sistema sin necesidad de consultar cada módulo por separado.

---

#### Accesos rápidos

Además de los indicadores operativos, el Dashboard ofrece accesos directos a las funcionalidades más utilizadas.

Entre ellos se encuentran:

- Gestión de Clientes;
- Gestión de Pedidos;
- Gestión de Ubicaciones;
- Gestión de Rutas;
- Centro de Operaciones Logísticas.

Estos accesos reducen el número de pasos necesarios para iniciar una tarea.

---

#### Arquitectura visual

La interfaz del Dashboard se organiza en tres áreas principales:

```text
┌─────────────────────────────────────────────────────────────┐
│ Encabezado                                                  │
├─────────────────────────────────────────────────────────────┤
│ Indicadores Generales                                       │
├─────────────────────────────────────────────────────────────┤
│ Accesos Rápidos                                             │
└─────────────────────────────────────────────────────────────┘
```

Esta distribución permite identificar rápidamente el estado general del sistema y acceder a los módulos disponibles.

---

#### Indicadores operativos

Los indicadores se presentan mediante tarjetas informativas ubicadas en la parte superior del Dashboard. Cada una muestra una métrica relevante para la operación.

Ejemplo:

```text
┌──────────────────────┐
│ Pedidos Pendientes   │
│         18           │
└──────────────────────┘

┌──────────────────────┐
│ Listos para Despacho │
│          7           │
└──────────────────────┘

┌──────────────────────┐
│ Despachos Activos    │
│          4           │
└──────────────────────┘

┌──────────────────────┐
│ Entregados Hoy       │
│         15           │
└──────────────────────┘
```

Los valores se actualizarán con la información proporcionada por el backend.

---

#### Accesos funcionales

En la parte inferior del Dashboard se presentan accesos rápidos mediante tarjetas o botones de navegación.

Ejemplo:

```text
[ Gestión de Clientes ]

[ Gestión de Pedidos ]

[ Gestión de Ubicaciones ]

[ Gestión de Rutas ]

[ Centro de Operaciones Logísticas ]
```

Cada acceso dirige al operador al módulo correspondiente.

---

#### Experiencia de usuario

El Dashboard está diseñado para ofrecer una visión clara de la operación sin sobrecargar la interfaz con información innecesaria.

La distribución de los elementos prioriza la claridad visual, la rapidez de consulta y la facilidad de navegación, permitiendo al operador comprender el estado del sistema e iniciar sus actividades en pocos segundos.

---

#### Relación con la arquitectura del frontend

El Dashboard está compuesto por componentes reutilizables de React encargados de mostrar indicadores y accesos funcionales.

La información es obtenida mediante la API REST del backend, mientras que el frontend se limita a presentar los datos y facilitar la navegación hacia los diferentes módulos, manteniendo la separación de responsabilidades definida para la arquitectura de TechSupply SCM.

### 4.2 Gestión de Clientes

#### Objetivo

Administrar la información de los clientes que podrán realizar pedidos dentro del sistema.

Todo pedido deberá estar asociado a un cliente previamente registrado; por ello, este módulo constituye el punto de inicio del flujo comercial cuando el destinatario aún no existe en la base de datos.

---

#### Responsabilidad del módulo

Este módulo es responsable de la administración de clientes.

Entre sus funciones se encuentran:

- registrar nuevos clientes;
- consultar clientes existentes;
- actualizar información;
- desactivar clientes;
- facilitar su selección durante la creación de pedidos.

No administra pedidos, despachos ni información relacionada con el inventario.

---

#### Ubicación dentro del flujo operativo

El módulo puede utilizarse en cualquier momento; sin embargo, su participación habitual dentro del proceso es la siguiente:

```text
Cliente no registrado

↓

Gestión de Clientes

↓

Registrar Cliente

↓

Crear Pedido
```

Si el cliente ya existe, el operador podrá continuar directamente con la creación del pedido.

---

#### Operaciones disponibles

El módulo permite realizar las siguientes operaciones.

##### Consultar clientes

Presenta un listado de clientes activos registrados en el sistema.

Desde esta pantalla es posible:

- visualizar información general;
- buscar clientes;
- acceder a la edición;
- registrar nuevos clientes.

---

##### Registrar cliente

Permite ingresar la información necesaria para crear un nuevo cliente.

La interfaz solicitará únicamente los datos requeridos por el backend, entre ellos:

- nombre;
- identificación;
- teléfono;
- correo electrónico;
- dirección;
- ubicación.

Al finalizar el registro, la información será enviada al backend y se notificará el resultado de la operación.

---

##### Editar cliente

Permite modificar la información de un cliente previamente registrado.

La interfaz cargará automáticamente los datos existentes para actualizar únicamente los campos necesarios, mientras que las validaciones de negocio permanecerán centralizadas en la API REST.

---

##### Desactivar cliente

Los clientes no serán eliminados físicamente.

Cuando el operador seleccione la opción de eliminar, el sistema realizará una desactivación lógica del registro. De esta forma, el cliente dejará de aparecer en los listados operativos, pero conservará la trazabilidad de los pedidos asociados.

---

#### Flujo funcional del módulo

El comportamiento esperado es el siguiente:

```text
Abrir módulo Clientes

↓

Consultar listado

↓

Seleccionar acción

        ├───────────────┐
        │               │
        ▼               ▼

Crear Cliente      Editar Cliente

        │               │
        ▼               ▼

Guardar Información

        │
        ▼

Actualizar listado

        │
        ▼

Mostrar notificación
```

Al finalizar cualquier operación, el sistema regresará al listado principal del módulo.

---

#### Relación con otros módulos

La información registrada será utilizada posteriormente por:

- Gestión de Pedidos, para seleccionar el cliente asociado al pedido;
- Gestión de Despachos, para obtener la ubicación de destino utilizada durante el cálculo de rutas.

La consistencia de estos datos resulta fundamental para el correcto funcionamiento del proceso logístico.

---

#### Principios de diseño aplicados

La interfaz del módulo sigue los principios generales definidos para el sistema:

- simplicidad visual;
- formularios claros;
- navegación consistente;
- validaciones inmediatas;
- notificaciones informativas;
- acciones claramente diferenciadas.

Estos principios permiten administrar clientes de forma rápida y con el menor número posible de interacciones.

### 4.3 Gestión de Ubicaciones

#### Objetivo

Administrar las ubicaciones geográficas utilizadas por el sistema para representar los distintos puntos de operación de la red logística de TechSupply SCM.

Estas ubicaciones serán compartidas por varios módulos y constituirán la base del grafo empleado para el cálculo de rutas dentro del sistema.

---

#### Responsabilidad del módulo

Este módulo es responsable de administrar las ubicaciones registradas en el sistema.

Entre sus principales funciones se encuentran:

- registrar nuevas ubicaciones;
- consultar ubicaciones existentes;
- actualizar información;
- desactivar ubicaciones.

No administra las conexiones entre ubicaciones ni realiza el cálculo de rutas, responsabilidades que corresponden al módulo de Gestión de Rutas y al servicio de Logística del backend.

---

#### Importancia dentro del sistema

Las ubicaciones representan los distintos puntos físicos que intervienen en el proceso de distribución.

Entre ellos se encuentran:

- ciudades;
- sucursales;
- centros de distribución;
- bodegas;
- puntos de entrega.

Cada ubicación constituye un nodo dentro del grafo logístico utilizado para calcular la ruta óptima de los despachos. Por ello, la correcta administración de este módulo resulta esencial para el funcionamiento del sistema.

---

#### Relación con el proceso logístico

Las ubicaciones participan en distintas etapas del flujo operativo:

```text
Registrar Ubicación

↓

Asignar ubicación al Cliente

↓

Crear Pedido

↓

Crear Despacho

↓

Calcular Ruta Óptima
```

Aunque su administración suele realizarse con poca frecuencia, la información registrada es utilizada continuamente durante la operación diaria.

---

#### Operaciones disponibles

El módulo permite realizar las siguientes operaciones.

##### Consultar ubicaciones

Desde esta pantalla es posible:

- visualizar información general;
- buscar ubicaciones;
- acceder a la edición;
- registrar nuevas ubicaciones.

---

##### Registrar ubicación

Permite crear nuevas ubicaciones dentro del sistema.

Inicialmente, el formulario solicitará únicamente el nombre de la ubicación.

La arquitectura del sistema permitirá incorporar en futuras versiones información adicional, como:

- provincia;
- ciudad;
- coordenadas geográficas;
- zona logística;
- observaciones.

Esta estructura facilita la evolución del módulo sin modificar su funcionamiento general.

---

##### Editar ubicación

Permite actualizar la información de una ubicación existente.

La interfaz cargará los datos actuales para modificar únicamente los campos necesarios, mientras que las validaciones relacionadas con duplicidad de nombres y reglas de negocio permanecerán centralizadas en el backend.

---

##### Desactivar ubicación

Las ubicaciones no serán eliminadas físicamente.

Cuando el operador seleccione la opción de eliminar, el sistema realizará una desactivación lógica del registro, preservando la integridad histórica de clientes, pedidos y despachos asociados a esa ubicación.

---

#### Flujo funcional del módulo

```text
        ▼               ▼

Guardar Información

        │
        ▼

Actualizar listado

        │
        ▼

Mostrar notificación
```

Al finalizar cualquier operación, el sistema regresará al listado principal del módulo.

---

#### Relación con otros módulos

La información administrada en este módulo será utilizada posteriormente por:

- Gestión de Clientes, para asignar la ubicación asociada al cliente;
- Gestión de Rutas, para definir los nodos de la red logística;
- Gestión de Despachos, durante el cálculo de la ruta óptima entre la bodega de origen y el destino del pedido.

Por esta razón, este módulo constituye uno de los pilares de la infraestructura logística de TechSupply SCM.

---

#### Principios de diseño aplicados

La interfaz sigue los principios generales definidos para el frontend:

- simplicidad visual;
- navegación consistente;
- formularios claros;
- acciones fácilmente identificables;
- notificaciones informativas;
- validaciones delegadas al backend.

Estos principios permiten administrar las ubicaciones de forma sencilla, manteniendo una base de información confiable para el funcionamiento del resto de módulos logísticos.

### 4.4 Gestión de Pedidos

#### Objetivo

Administrar los pedidos generados por los clientes y controlar su ciclo de vida dentro del proceso de logística de salida (Outbound).

Cada pedido representa el documento comercial que agrupa los productos solicitados por un cliente y constituye el punto de partida para la preparación y posterior despacho de la mercancía. Por ello, este módulo actúa como el núcleo del proceso comercial dentro del MVP de TechSupply SCM.

---

#### Responsabilidad del módulo

Este módulo es responsable de administrar la información general de los pedidos.

Entre sus principales funciones se encuentran:

- consultar pedidos;
- registrar nuevos pedidos;
- actualizar la información general;
- desactivar pedidos cuando corresponda;
- iniciar el proceso de incorporación de productos.

La administración de los productos asociados al pedido se realizará en el Workspace de Detalles de Pedido.

---

#### Importancia dentro del sistema

El pedido constituye el documento central del proceso de logística de salida, ya que todas las etapas posteriores dependen de su correcta creación.

Su ciclo de vida puede representarse de la siguiente manera:

```text
Cliente

↓

Pedido

↓

Detalles del Pedido

↓

Pedido Listo para Despacho

↓

Despacho

↓

Entrega
```

Sin un pedido válido no es posible iniciar ninguna operación logística.

---

#### Información administrada

En esta etapa únicamente se registra la información general del pedido.

Entre los principales datos se incluyen:

- cliente;
- vendedor responsable;
- fecha;
- observaciones.

Los productos no se incorporan en esta pantalla, sino posteriormente en el Workspace de Detalles de Pedido.

---

#### Operaciones disponibles

El módulo permite realizar las siguientes operaciones.

##### Consultar pedidos

Presenta un listado con los pedidos registrados.

Desde esta pantalla es posible:

- visualizar información general;
- buscar pedidos;
- filtrar por estado;
- registrar nuevos pedidos;
- editar pedidos cuando el estado lo permita;
- acceder al Workspace de Detalles de Pedido.

---

##### Registrar pedido

Permite crear un nuevo pedido seleccionando previamente un cliente registrado.

Inicialmente el documento contendrá únicamente la información general. Una vez completado el registro, el sistema redirigirá automáticamente al Workspace de Detalles de Pedido para continuar con la incorporación de productos.

---

##### Editar pedido

Permite modificar únicamente la información general del pedido.

Esta operación estará disponible cuando el estado del pedido lo permita, de acuerdo con las reglas de negocio definidas por el backend.

---

##### Desactivar pedido

Cuando las reglas del proceso lo permitan, el pedido podrá desactivarse mediante una eliminación lógica.

De esta forma, la información permanecerá almacenada para conservar la trazabilidad de las operaciones realizadas.

---

#### Flujo funcional del módulo

El comportamiento esperado es el siguiente:

```text
Abrir módulo Pedidos

↓

Consultar listado

↓

Seleccionar acción

        ├────────────────────────┐
        │                        │
        ▼                        ▼

Crear Pedido             Editar Pedido

        │                        │
        ▼                        ▼

Guardar Información

        │
        ▼

Pedido creado correctamente

        │
        ▼

Abrir Workspace de Detalles
```

A diferencia de otros módulos, la creación de un pedido no finaliza regresando al listado principal, sino que continúa automáticamente con la siguiente etapa del proceso.

---

#### Continuidad del flujo operativo

Una vez creado el pedido, el siguiente paso consiste en registrar los productos que lo conforman.

Para mantener la continuidad del proceso, el frontend redirige automáticamente al Workspace de Detalles de Pedido.

```text
Crear Pedido

↓

Toast

"Pedido creado correctamente"

↓

Workspace

Detalles del Pedido

↓

Comenzar a registrar productos
```

Esta transición evita que el operador deba regresar al listado para localizar nuevamente el pedido recién creado.

---

#### Estados generales del pedido

Durante su ciclo de vida, el pedido evoluciona entre distintos estados definidos por el backend.

Entre ellos se encuentran:

- PENDIENTE;
- PREPARANDO;
- LISTO_PARA_DESPACHO;
- EN_DESPACHO;
- ENTREGADO.

La interfaz utiliza estos estados para habilitar o restringir las acciones disponibles, mientras que las reglas de transición permanecen centralizadas en la API REST.

---

#### Relación con otros módulos

La información administrada en este módulo será utilizada posteriormente por:

- Workspace de Detalles de Pedido, para incorporar los productos asociados;
- Gestión de Despachos, para preparar la distribución de la mercancía;
- Centro de Operaciones Logísticas, para calcular la ruta óptima cuando el pedido esté listo para despacho.

Este módulo constituye el vínculo entre la gestión comercial y la operación logística.

---

#### Principios de diseño aplicados

La interfaz sigue los principios generales definidos para el frontend:

- simplicidad visual;
- continuidad del flujo operativo;
- navegación intuitiva;
- acceso directo al Workspace de Detalles de Pedido;
- acciones contextualizadas según el estado;
- validaciones delegadas al backend.

Estos principios permiten iniciar el proceso comercial y continuar de forma fluida hacia el registro de los productos del pedido, reduciendo interrupciones y cambios innecesarios de contexto.

### 4.5 Workspace de Detalles de Pedido

#### Objetivo

Administrar los productos que conforman un pedido mediante un Workspace diseñado para permitir al operador completar la construcción del documento desde una única pantalla de trabajo.

A diferencia del módulo de Gestión de Pedidos, cuya responsabilidad se limita a administrar la información general del documento, este Workspace gestiona los productos asociados al pedido.

Su diseño busca ofrecer una experiencia de edición continua, evitando cambios innecesarios de pantalla y favoreciendo un flujo de trabajo más eficiente.

---

#### Responsabilidad del módulo

Este módulo será responsable exclusivamente de la administración de los detalles del pedido.

Entre sus principales funciones se encuentran:

- consultar los productos asociados al pedido;
- agregar nuevos productos;
- modificar cantidades (no precios);
- eliminar productos (detalle pedido);
- calcular automáticamente los subtotales (lo hace el backend internamente);
- mantener actualizado el resumen del pedido (llamar internamente al empoint luego del proceso).

No será responsable de modificar la información general del pedido ni de ejecutar procesos logísticos posteriores.

---

#### Importancia dentro del sistema

### 4.6 Gestión de Rutas

#### Objetivo

Administrar la red de conexiones entre las ubicaciones registradas en el sistema.

Cada ruta representa una conexión directa entre un origen y un destino, indicando la distancia existente entre ambos puntos. Esta información constituye la base utilizada posteriormente por el algoritmo de búsqueda de rutas para calcular el recorrido óptimo durante el proceso de despacho.

---

#### Responsabilidad del módulo

El módulo será responsable exclusivamente de administrar la red logística utilizada por el sistema.

Entre sus principales funciones se encuentran:

- registrar nuevas rutas;
- consultar las rutas existentes;
- actualizar la información de una ruta;
- eliminar rutas que ya no sean válidas.

No será responsable de calcular recorridos ni ejecutar procesos de optimización, responsabilidades que corresponden al servicio logístico del backend.

---

#### Importancia dentro del sistema

Las rutas representan la estructura física de la red de distribución de TechSupply SCM y definen cómo pueden comunicarse las diferentes ubicaciones registradas.

Su participación dentro del proceso operativo puede representarse de la siguiente manera:

```text
Ubicaciones

↓

Rutas

↓

Red Logística

↓

Algoritmo A*

↓

Ruta Óptima

↓

Despacho
```

Sin una red de rutas correctamente configurada no será posible calcular recorridos válidos para realizar los despachos.

---

#### Concepto de ruta

Una ruta representa la conexión entre dos ubicaciones de la red logística.

Cada registro almacenará, como mínimo:

- ubicación de origen;
- ubicación de destino;
- distancia en kilómetros.

Conceptualmente, una ruta puede representarse de la siguiente manera:

```text
Calceta

────────────── 12.5 km ──────────────►

Tosagua
```

Estas conexiones permitirán construir posteriormente el grafo utilizado por el algoritmo de búsqueda de rutas.

---

#### Relación con otros módulos

La Gestión de Rutas depende directamente del módulo de Gestión de Ubicaciones, ya que únicamente podrán registrarse conexiones entre ubicaciones existentes.

Posteriormente, la información administrada será utilizada por el proceso de despacho para construir la red logística empleada durante el cálculo de la ruta óptima.

De esta manera, este módulo actúa como enlace entre la administración de ubicaciones y el proceso logístico de distribución.

---

#### Operaciones disponibles

El módulo permitirá realizar las siguientes operaciones sobre la red logística.

##### Consultar rutas

Presenta el listado de rutas registradas junto con su información principal:

- origen;
- destino;
- distancia;
- acciones disponibles.

El listado facilita la consulta de la estructura actual de la red logística.

##### Registrar ruta

Permite crear una nueva conexión entre dos ubicaciones.

El operador deberá indicar:

- ubicación de origen;
- ubicación de destino;
- distancia en kilómetros.

Una vez validada la información, el sistema registrará la ruta y actualizará automáticamente el listado.

##### Actualizar ruta

Permite modificar la información de una ruta existente utilizando el mismo formulario empleado durante el registro.

Podrán modificarse:

- origen;
- destino;
- distancia.

Los cambios serán persistidos inmediatamente después de confirmar la operación.

##### Eliminar ruta

Permite retirar una conexión de la red logística previa confirmación del operador.

Una vez eliminada, la ruta dejará de formar parte de la información utilizada durante el cálculo de recorridos.

---

#### Arquitectura visual

La Gestión de Rutas utilizará una interfaz orientada a la administración de información.

A diferencia del Workspace de Detalles de Pedido, este módulo organiza sus operaciones mediante una pantalla administrativa compuesta por cuatro áreas principales.

##### Distribución general

```text
┌─────────────────────────────────────────────────────────────┐
│ Encabezado                                                  │
├─────────────────────────────────────────────────────────────┤
│ Barra de Acciones                                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│                 Tabla de Rutas                              │
│                                                             │
├─────────────────────────────────────────────────────────────┤

└─────────────────────────────────────────────────────────────┘
```

Esta organización permite consultar y administrar las rutas desde una única pantalla.

##### Encabezado

Identifica el módulo y proporciona contexto permanente al operador.

Ejemplo:

```text

Administra la red logística utilizada para el cálculo de recorridos.
```

##### Tabla de rutas

Representa el elemento principal de la interfaz.

Cada fila corresponde a una ruta registrada y muestra:

- origen;

La información se actualiza automáticamente después de cada operación.

##### Formulario integrado

Ubicado debajo de la tabla, permite registrar o editar rutas utilizando un único componente reutilizable.

#### Experiencia de usuario

La interfaz prioriza la simplicidad y la rapidez de uso, permitiendo administrar la red logística sin abandonar la pantalla principal.

Cada operación mostrará una notificación con el resultado correspondiente.

En caso de error, se presentarán mensajes claros sin exponer detalles técnicos del sistema.

#### Relación con la arquitectura del frontend

El módulo estará compuesto por componentes React reutilizables y utilizará la capa de servicios para consumir la API REST.

Aunque el operador únicamente administra conexiones entre ubicaciones, la calidad y consistencia de esta información influirá directamente en el cálculo de las rutas óptimas y en el funcionamiento general del proceso logístico de TechSupply SCM.

### 4.7 Centro de Operaciones Logísticas

El Centro de Operaciones Logísticas representa la etapa final del proceso **Outbound** de TechSupply SCM.

En este módulo el operador inicia la distribución de los pedidos preparados, administra los despachos registrados y consulta la información generada durante la planificación logística.

A diferencia de los módulos administrativos, cuya finalidad es registrar y gestionar información, este módulo coordina el inicio y seguimiento del proceso de distribución. Su diseño permite al operador trabajar sobre los despachos sin conocer los procesos internos ejecutados por el backend, presentando únicamente la información necesaria para la toma de decisiones y el control de la operación.

---

#### 4.7.1 Objetivo

Permitir al operador gestionar el ciclo de vida de los despachos, desde la selección de un pedido listo para distribución hasta el seguimiento de la información generada durante la planificación logística.

Para ello, el módulo permitirá:

- consultar los pedidos disponibles para despacho;
- crear nuevos despachos;
- administrar los despachos registrados;
- ejecutar las acciones permitidas según su estado;
- visualizar el resumen operativo generado por el backend.

Toda la planificación logística permanecerá centralizada en el backend. El frontend será responsable únicamente de coordinar la interacción con el operador y presentar la información recibida mediante la API.

---

#### 4.7.2 Responsabilidades

El Centro de Operaciones Logísticas será responsable de:

- mostrar los pedidos disponibles para despacho;
- permitir la creación de nuevos despachos;
- consultar la información general de los despachos registrados;
- mostrar el estado operativo de cada despacho;
- habilitar las acciones permitidas según el estado del despacho;
- presentar el resultado de la planificación logística generado por el backend.

No realizará cálculos de rutas, validaciones logísticas ni aplicará reglas de negocio. Estas responsabilidades permanecerán exclusivamente en el backend, manteniendo una separación clara entre la interfaz de usuario y la lógica del sistema.

---

#### 4.7.3 Flujo Operativo

El Centro de Operaciones Logísticas concentra todas las actividades relacionadas con la creación y seguimiento de los despachos dentro de una única área de trabajo.

Al ingresar al módulo, el operador podrá consultar los pedidos listos para distribución, crear nuevos despachos y supervisar las operaciones ya registradas.

El flujo operativo será el siguiente:

```text

            ▼

            │
            ▼

            ▼

            │
            ▼

            │
            ▼

            │
            ▼

Aceptar

            │
            ▼

Consultar Gestión de Despachos
```

Este flujo concentra toda la interacción necesaria para iniciar un despacho sin exponer al operador los procesos internos ejecutados por el backend.

##### Selección del Pedido

La interfaz mostrará únicamente los pedidos que cumplen las condiciones necesarias para iniciar un despacho.

Una vez seleccionado un pedido, el operador podrá iniciar el proceso mediante una única acción, evitando interpretar manualmente las reglas de negocio.

##### Creación del Despacho

Al seleccionar **Crear Despacho**, el frontend enviará una única solicitud al backend.

Mientras la operación se ejecuta, la interfaz mostrará un indicador de carga y deshabilitará temporalmente la acción para evitar solicitudes duplicadas. El operador no deberá realizar ninguna acción adicional hasta recibir la respuesta del sistema.

##### Presentación del Resultado

Finalizado el proceso, el backend devolverá la información del despacho generado.

El frontend presentará un resumen con los principales datos de la operación. Esta ventana tendrá un propósito exclusivamente informativo y permitirá al operador verificar el resultado antes de continuar con su trabajo.

Al seleccionar **Aceptar**, la ventana se cerrará y el sistema regresará automáticamente al Centro de Operaciones Logísticas.

##### Continuidad del Proceso

Después de crear un despacho, el operador podrá continuar administrando los pedidos pendientes o consultar el estado de los despachos existentes.

De esta manera, el módulo mantiene un flujo continuo de trabajo sin necesidad de abandonar la misma área funcional.

Ambas vistas conforman el flujo operativo del Centro de Operaciones Logísticas y proporcionan una visión continua del proceso de distribución.

#### 4.7.6 Arquitectura Visual

##### Objetivo

El Centro de Operaciones Logísticas está diseñado para ofrecer una vista clara del proceso de distribución, permitiendo al operador localizar rápidamente la información relevante y ejecutar las acciones correspondientes sin abandonar el contexto de trabajo.

Su organización visual prioriza la consulta del estado de las operaciones y mantiene una estructura consistente con el resto de los módulos del sistema.

---

##### Organización General

El módulo se divide en dos vistas complementarias:

- **Pedidos Disponibles**, orientada al inicio de nuevos despachos.
- **Gestión de Despachos**, destinada al seguimiento y administración de los despachos registrados.

Aunque ambas cumplen objetivos distintos, comparten la misma organización visual para ofrecer una experiencia uniforme.

---

##### Estructura Común

Las dos vistas seguirán la siguiente distribución:

```text
┌──────────────────────────────────────────────────────────────┐
│ Encabezado                                                   │
├──────────────────────────────────────────────────────────────┤
│ Barra de Acciones y Filtros                                  │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│                   Tabla Principal                            │
│                                                              │
├──────────────────────────────────────────────────────────────┤
│ Estado del Listado / Paginación                              │
└──────────────────────────────────────────────────────────────┘
```

Cada área cumple una responsabilidad específica, manteniendo la interfaz organizada incluso cuando aumenta el volumen de información.

---

##### Encabezado

El encabezado identifica la vista activa y proporciona contexto permanente al operador.

Mostrará:

- nombre de la pantalla;
- descripción breve de su propósito.

Ejemplo:

```text
Centro de Operaciones Logísticas

Administra la distribución y seguimiento de los pedidos.
```

---

##### Barra de Acciones

Ubicada debajo del encabezado, facilita la consulta de la información.

Según la vista, podrá incluir:

- búsqueda por número de pedido o despacho;
- filtros por estado;
- actualización del listado.

Estas acciones estarán orientadas únicamente a la consulta y no modificarán el estado de los registros.

---

##### Tabla Principal

La mayor parte del espacio estará ocupada por una tabla que mostrará la información principal del módulo.

Dependiendo de la vista seleccionada, representará:

- pedidos disponibles para despacho; o
- despachos registrados.

Cada fila concentrará la información y las acciones disponibles para el registro correspondiente.

---

##### Indicadores de Estado

El estado de cada registro se representará mediante indicadores visuales que permitan identificar rápidamente su situación.

El diseño específico de estos indicadores será definido posteriormente en el Sistema de Diseño del frontend para mantener una apariencia consistente en toda la aplicación.

---

##### Consistencia Visual

El Centro de Operaciones Logísticas reutiliza la misma estructura de navegación y distribución aplicada en los demás módulos administrativos.

Esta uniformidad reduce la curva de aprendizaje, facilita la navegación entre pantallas y mantiene una experiencia de usuario coherente en todo TechSupply SCM.

#### 4.7.7 Estados del Despacho

##### Objetivo

Los estados del despacho representan la etapa actual del proceso de distribución y determinan las acciones que el operador puede realizar en cada momento.

La interfaz utilizará esta información para mostrar únicamente las operaciones compatibles con el estado actual del despacho, mientras que las reglas de transición permanecerán centralizadas en el backend.

---

##### Ciclo de Vida del Despacho

Durante su ejecución, un despacho recorrerá la siguiente secuencia de estados:

```text
CREADO

      │

      ▼

EN_TRÁNSITO

      │

      ▼

ENTREGADO
```

De forma excepcional, un despacho también podrá finalizar en estado **CANCELADO**, cuando las reglas de negocio lo permitan.

```text
CREADO

      │

      ├────────────► CANCELADO

      │

      ▼

EN_TRÁNSITO

      │

      ▼

ENTREGADO
```

Este flujo representa la evolución normal de una operación logística dentro del sistema.

---

##### Estado: CREADO

Corresponde al momento en que el backend finaliza la planificación logística y registra el nuevo despacho.

En este estado:

- el despacho ya existe en el sistema;
- la ruta ha sido asignada;
- la operación está lista para iniciar su distribución.

El operador podrá consultar la información del despacho y, cuando corresponda, iniciar el proceso de entrega.

---

##### Estado: EN_TRÁNSITO

Indica que el despacho ha iniciado su recorrido hacia el destino.

Durante esta etapa, el operador podrá consultar el estado de la operación y ejecutar únicamente las acciones permitidas para un despacho en curso.

La disponibilidad de estas acciones será determinada por el backend.

---

##### Estado: ENTREGADO

Representa la finalización exitosa del proceso de distribución.

A partir de este momento, el despacho pasará a formar parte del historial operativo y no admitirá nuevas modificaciones relacionadas con su ejecución, aunque permanecerá disponible para consultas y fines de trazabilidad.

---

##### Estado: CANCELADO

Representa la interrupción del proceso logístico antes de completar la entrega.

La cancelación solo podrá realizarse cuando las reglas de negocio definidas por el backend lo permitan.

El despacho permanecerá registrado con fines históricos, pero dejará de participar en el flujo operativo.

---

##### Representación en la Interfaz

Cada estado se mostrará mediante un indicador visual que permita identificar rápidamente la situación del despacho desde el listado principal.

El diseño de estos indicadores será definido posteriormente en el Sistema de Diseño del frontend para mantener una representación uniforme en toda la aplicación.

---

##### Relación con las Acciones del Operador

Las acciones disponibles dentro del Centro de Operaciones Logísticas dependerán siempre del estado actual del despacho.

Este comportamiento guía al operador durante el proceso de distribución, mostrando únicamente las operaciones válidas para cada etapa y reduciendo la posibilidad de errores durante la gestión de los despachos.

---

#### 4.7.8 Integración con el Backend

##### Objetivo

El Centro de Operaciones Logísticas constituye el punto de interacción entre el operador y el proceso de despacho implementado por el backend.

Todas las operaciones se realizarán mediante la API REST. El frontend se limitará a presentar la información, enviar las acciones del usuario y mostrar los resultados devueltos por los servicios del sistema, sin implementar lógica de negocio ni algoritmos de optimización.

---

##### Separación de Responsabilidades

La arquitectura de TechSupply SCM establece una clara separación entre el frontend y el backend.

El frontend será responsable de:

- mostrar la información disponible;
- capturar las acciones del operador;
- consumir la API REST;
- presentar mensajes de éxito o error;
- actualizar la interfaz según la respuesta recibida.

El backend será responsable de:

- validar las operaciones;
- ejecutar el proceso logístico;
- calcular la ruta óptima;
- administrar el ciclo de vida de los despachos;
- almacenar la información generada.

Esta separación favorece una arquitectura modular, escalable y de fácil mantenimiento.

---

##### Creación de un Despacho

Cuando el operador seleccione **Crear Despacho**, el frontend enviará una única solicitud al backend.

A partir de ese momento, el backend ejecutará todo el proceso logístico mientras la interfaz mostrará indicadores de carga para informar el estado de la operación y evitar solicitudes duplicadas.

Una vez recibida la respuesta, el frontend actualizará automáticamente la información mostrada.

---

##### Procesos Internos del Backend

La creación de un despacho puede involucrar diversos servicios internos del backend, completamente transparentes para el frontend.

Entre ellos podrán ejecutarse procesos como:

- validación del pedido;
- verificación de estados;
- construcción del grafo logístico;
- cálculo de la ruta óptima;
- registro del despacho;
- actualización del estado del pedido;
- almacenamiento de la información.

El frontend interactuará exclusivamente con la API REST, sin conocer la implementación interna de estos procesos.

---

##### Independencia del Servicio de Optimización

El algoritmo encargado de calcular la ruta óptima podrá ejecutarse como un servicio independiente del backend.

Desde la perspectiva del frontend, esta implementación será completamente transparente, ya que únicamente recibirá el resultado final del proceso.

Este desacoplamiento permitirá evolucionar el algoritmo de optimización sin afectar la interfaz de usuario.

---

##### Presentación del Resultado

Al finalizar la creación del despacho, el frontend mostrará un resumen con la información devuelta por el backend.

Entre los datos presentados podrán incluirse:

- identificador del despacho;
- pedido asociado;
- ruta asignada;
- distancia total estimada;
- estado inicial del despacho.

La interfaz mostrará esta información sin realizar cálculos ni modificaciones sobre los datos recibidos.

---

##### Confirmación y Actualización

Después de revisar el resumen, el operador cerrará la ventana mediante la acción **Aceptar**.

Esta acción únicamente cerrará el cuadro de diálogo y permitirá continuar trabajando; no enviará nuevas solicitudes ni modificará el estado del despacho.

Al cerrarse la ventana, la interfaz actualizará automáticamente:

- el listado de despachos;
- el estado del pedido asociado;
- la lista de pedidos disponibles;
- los indicadores visibles del módulo.

De esta manera, la información permanecerá sincronizada sin necesidad de recargar la pantalla.

---

##### Manejo de Errores

Si el backend detecta una situación que impida completar el despacho, el frontend mostrará un mensaje claro indicando que la operación no pudo realizarse.

La interfaz evitará exponer detalles técnicos de implementación y comunicará únicamente la información necesaria para que el operador pueda continuar con su trabajo.

---

##### Beneficios Arquitectónicos

La separación entre la interfaz y los servicios internos del backend aporta ventajas como:

- independencia entre presentación y lógica de negocio;
- evolución del algoritmo de optimización sin modificar el frontend;
- incorporación de nuevos servicios sin afectar la experiencia del usuario;
- mayor mantenibilidad gracias a la separación de responsabilidades;
- escalabilidad para futuras versiones del sistema.

Esta arquitectura permite que el Centro de Operaciones Logísticas evolucione sin comprometer la estabilidad de la interfaz.

#### 4.7.9 Experiencia de Usuario

##### Objetivo

El Centro de Operaciones Logísticas ha sido diseñado para ofrecer una experiencia de trabajo clara, eficiente y orientada a procesos.

La interfaz busca reducir la carga operativa del usuario, proporcionando únicamente la información y las acciones necesarias para gestionar el ciclo de vida de los despachos.

---

##### Flujo Guiado

La interfaz acompaña al operador durante cada etapa del proceso logístico, mostrando únicamente las acciones compatibles con el estado actual de cada despacho.

Este enfoque simplifica la operación, reduce la posibilidad de errores y facilita el aprendizaje del sistema por parte de nuevos usuarios.

---

##### Organización de la Información

La información se distribuye en dos vistas complementarias:

- **Pedidos Disponibles**, destinada al inicio de nuevos despachos.
- **Gestión de Despachos**, orientada al seguimiento de las operaciones ya registradas.

Esta separación permite distinguir claramente las actividades de creación y seguimiento, facilitando la comprensión del flujo logístico.

Esta retroalimentación permite al operador conocer el estado de cada operación en todo momento.

##### Minimización de Acciones

La interfaz está diseñada para completar cada proceso con el menor número posible de interacciones.

Después de cada operación, la información se actualiza automáticamente, evitando recargas manuales y permitiendo que el operador continúe trabajando sin interrupciones.

Asimismo, las acciones de uso frecuente permanecen accesibles desde la vista principal del módulo.

##### Claridad en la Comunicación

Los mensajes presentados al operador utilizan un lenguaje sencillo y orientado al proceso de negocio.

La interfaz evita mostrar información técnica sobre la implementación interna del sistema y comunica únicamente los datos necesarios para comprender el resultado de cada operación.

##### Continuidad del Flujo Operativo

Una vez finalizada una operación, el operador puede continuar administrando otros pedidos o despachos sin abandonar el Centro de Operaciones Logísticas.

Esta continuidad convierte al módulo en una estación de trabajo especializada para la gestión permanente del proceso de distribución.
